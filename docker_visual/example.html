    Lv1こんなアプリを動かす

    ToDo アプリのような、Web アプリ ＋ データベース。ブラウザで開く画面と処理（web）と、データを保存するデータベース（PostgreSQL）の2つでできています。

    Docker では、役割ごとにコンテナを分けます。公式にも「each container should do one thing and do it well」（各コンテナは1つのことをうまくやるべき）とあります。

    Windows コンテナでも、Web アプリは動かせます。ただし、DB コンテナの公式の例は見つかりませんでした。そこが、Linux コンテナとの一番の違いです。

    • web：Windows のベースイメージ（レジストリは mcr.microsoft.com）の上に作れる。
    • db：postgres の公式イメージ（Docker Hub）のページには、Windows の記載がない。SQL Server の公式コンテナイメージは、複数の解説で Linux 向けとされている。公式ページでの確認は未了

    図の赤い点線の箱が、「公式の例が見つからなかった」部分です。

    Windows コンテナで DB 付きにする形（筆者の整理・公式の例ではありません）
    ① ホストや別のマシンで動く DB に接続する　② DB だけを Linux コンテナで別に動かす　③ ファイル型の DB をボリュームに置く
    図の見方 点線の箱は「これから入る部品」です。章を読み進めると、全体像の図にあった部品が、1つずつ実際の名前で現れます。
    この例について
    公式ガイド（Node.js アプリ ＋ PostgreSQL）を簡略化した説明用の例です。サービス名や値は、そのまま使えるとは限りません。 Windows コンテナ側は、Microsoft Learn の公式ページ（分離モード・ネットワーク・永続ストレージ）に書かれている内容を、同じ形に当てはめたものです。丸ごと動かせる公式の例ではありません。

    Lv2イメージを用意する

    全体像の Lv4（イメージ・レジストリ）にあたる
    • web：あなたの Dockerfile からイメージを作る。
    • db：自分では作らない。レジストリ（Docker Hub）にある公式の postgres イメージを取ってくる（pull）。

    compose.yaml には、こう書きます。

    services:  web:    build: .            # 自分の Dockerfile からイメージを作る  db:    image: postgres:17  # レジストリの公式イメージを使う
    • web：Windows のベースイメージの上に作る。Rozeさんの dockerimage と同じ形です。
    • ベースイメージは、Microsoft のレジストリ mcr.microsoft.com から取ってくる。
    • db：公式の DB イメージの例が見つからない（図の赤い点線）。
    FROM mcr.microsoft.com/windows/servercore:ltsc2025COPY app C:/app/CMD ["…アプリを起動するコマンド…"]
    タグ（ltsc2025）は、ホストの Windows と合わせる
    プロセス分離では、ホストとイメージのビルド番号が違うと、起動がブロックされます。Hyper-V 分離なら、合わせなくても動かせます。（Windows 11 では例外もあります）
    ここで増えたもの web イメージ（自作）／ postgres イメージ（公式・レジストリから取得） web イメージ（Windows のベースイメージの上に自作）／ ベースイメージは mcr.microsoft.com から取得

    Lv3イメージからコンテナを作る

    全体像の Lv5（コンテナ）にあたる

    それぞれのイメージから、web コンテナと db コンテナができます。

    PostgreSQL の公式イメージは、POSTGRES_PASSWORD という環境変数が必須です（公式：「The only variable required is POSTGRES_PASSWORD」）。

      db:    image: postgres:17    environment:      POSTGRES_PASSWORD: example   # 必須。例では直接書いている（学習用）
    パスワードを直接書くのは、学習用です
    公式ガイドでは、パスワードを環境変数に直接書かず、secrets（秘密情報用の仕組み）のファイルから読み込んでいます。

    web イメージから、web コンテナができます。Windows コンテナには、分離モードが2つあります。

    • プロセス分離：ホストの Windows カーネルを共有する。--isolation=process
    • Hyper-V 分離：コンテナごとに軽量VM。--isolation=hyperv

    既定は、Windows Server ではプロセス分離、Windows 10 Pro / Enterprise では Hyper-V 分離です。Rozeさんの PC（Windows 11 Home）の既定は hyperv でした（2026/10/5 の実機確認）。

    DB コンテナは、図では「別の形で用意」
    Linux 版の db コンテナ（postgres ＋ 必須の環境変数）に当たる部分は、Windows コンテナでは、Lv1 の ①〜③ のように別の形で用意します。
    ここで増えたもの web コンテナ ← web イメージ ／ db コンテナ ← postgres イメージ ＋ 必須の環境変数 web コンテナ ← web イメージ（プロセス分離 または Hyper-V 分離）

    Lv4ネットワークでつなぐ

    全体像の Lv7（ネットワーク）にあたる

    Docker Compose は、ネットワークを自動で作ります（<プロジェクト名>_default という bridge）。全サービスがつながり、各サービスは名前を DNS に登録するので、サービス名で呼び合えます。

    公式の例：「The web service can connect to the database at postgres://db:5432.」

      web:    build: .    environment:      POSTGRES_HOST: db   # DB の場所 ＝ サービス名「db」（名前はアプリ側の決め事の例）# networks: は書かなくてよい（Compose が自動で作る）
    • 接続先は db:5432。IP アドレスではなく、サービス名で書きます（IP は、起動や再作成のたびに変わりうるため）。
    • コンテナどうしの通信では、コンテナ側のポート（5432）を使います。

    Windows コンテナの既定のネットワークは、bridge ではなく nat です。コンテナは内部の Hyper-V スイッチにつながり、サブネットから IP アドレスを受け取ります。

    • 名前での呼び合い：nat では「ローカルのサービス検出」に対応しています（公式の表：Local Service Discovery = YES）。
    • 制限：サブネットをまたぐ通信は非対応。別のホストのコンテナへは、ホストのポートを公開して届かせます。

    自分用のネットワークを作る例（公式）：

    docker network create -d "nat" --subnet "10.244.0.0/24" my_nat
    DB の接続先は、「DB をどう用意したか」で決まります
    ホストの DB なら、ホストの住所を指定します。DB だけを別のコンテナにするなら、その公開ポートへ。どの形でも、コンテナの中から見た「localhost」は、そのコンテナ自身を指します。一般的な説明
    ここで増えたもの ネットワーク ⊃ web コンテナ ＋ db コンテナ ／ web → db:5432 ネットワーク（nat）⊃ web コンテナ ／ web → DB の場所

    Lv5ブラウザから見えるようにする

    全体像の Lv7（ポート公開 -p）にあたる

    web は、ports でホストの 3000 番に公開します。ブラウザは localhost:3000 を開きます。

    db は、ports を書きません。ホストの外（ブラウザなど）からは直接届かず、同じネットワークの web からだけ db:5432 で届きます。

      web:    build: .    ports:      - "3000:3000"      # ホスト:コンテナ  db:    # ports は書かない ＝ 外には出さない
    • "3000:3000" は「ホスト側:コンテナ側」。左がホスト、右がコンテナです。
    • 公式：「The host port is only used when accessing the service from outside the network.」

    nat は、ホストからコンテナへのポート転送（マッピング）に対応しています。web を、ホストの 8080 番に公開します。ブラウザは localhost:8080 を開きます。

    docker run -d -p 8080:80 <web イメージ>   # ホスト:コンテナ
    • 8080:80 は「ホスト側:コンテナ側」。Linux コンテナと、書き方も同じです。
    • 80 番は、IIS など Web サーバーの代表的な待ち受けポートです（例）。
    ここで増えたもの ブラウザ → ホストの 3000 番 → web コンテナ ／ db は外に出さない ブラウザ → ホストの 8080 番 → web コンテナ（nat のポート転送）

    Lv6データを残す

    全体像の Lv8（ボリューム）にあたる

    DB コンテナの書き込み層に保存すると、コンテナを消すとデータも消えます。そこで、ボリューム db-data を、DB のデータ置き場にマウントします。

      db:    image: postgres:17    volumes:      - db-data:/var/lib/postgresql/datavolumes:  db-data:               # ボリュームを定義する
    • docker compose down：コンテナとネットワークを片付ける。名前付きボリュームは、既定では消えません。
    • docker compose down --volumes：ボリュームも消えます。
    つまずきやすい点：マウント先は、PostgreSQL のバージョンで違う
    17 以前は /var/lib/postgresql/data、18 以降は /var/lib/postgresql にマウントします。公式は「17 以下で /var/lib/postgresql にマウントすると、コンテナを作り直したときにデータが残らない」と警告しています。

    Windows コンテナでも、ボリュームと bind mount が使えます。違いは、Windows のパスで書くことです。

    名前付きボリューム（公式の手順）：

    docker volume create unwounddocker run -v unwound:c:\data <イメージ>   # c:\data にマウント

    bind mount（ホストのフォルダを見せる・公式）：

    docker run -v c:\ContainerData:c:\data:RO   # 読み取り専用docker run -v c:\ContainerData:c:\data:RW   # 読み書き可（既定）
    Windows 特有の注意
    ・権限：Hyper-V 分離では LocalSystem、プロセス分離ではコンテナ内のプロセスの権限（ACL）でアクセスされます。「アクセス拒否」になったら、ホスト側のフォルダの権限を確認します。
    ・パス：コンテナ側のパスは、小文字に変換されます（c:\MyData → c:\mydata）。
    ・安全：C:\ のような重要なディレクトリを、信頼できないコンテナに bind mount してはいけません。
    ここで増えたもの ボリューム db-data ← db コンテナのマウント先 ボリューム（または bind mount）← web コンテナの c:\data

    Lv7全部を1ファイルに：Docker Compose

    ここまでの設定を、1つの compose.yaml にまとめます。複数の docker run を打たなくても、1コマンドで、ネットワークと全コンテナが作られます。

    services:  web:    build: .    ports:      - "3000:3000"    environment:      POSTGRES_HOST: db      POSTGRES_USER: postgres      POSTGRES_DB: example      POSTGRES_PASSWORD: example    depends_on:      - db              # db を先に起動する  db:    image: postgres:17    volumes:      - db-data:/var/lib/postgresql/data    environment:      POSTGRES_DB: example      POSTGRES_PASSWORD: examplevolumes:  db-data:
    やりたいことコマンド
    ビルドして、まとめて起動docker compose up -d --build
    状態を見るdocker compose ps
    止めて片付ける（ボリュームは残る）docker compose down
    ボリュームも消すdocker compose down --volumes
    補足
    ・環境変数の名前（POSTGRES_HOST など）は、アプリ側の決め事の例です。実際のコードに合わせてください。
    ・depends_on は起動順の指定です。DB の「準備完了」まで待つには、公式ガイドのように healthcheck と condition: service_healthy を使います。
    ・Rozeさんの PC は今 Windows コンテナのモードです（2026/10/5 の実機確認）。この Linux 版を試すには、Linux コンテナ（WSL 2）に切り替える必要があります。

    Windows コンテナでも、Docker Compose の考え方は同じです（サービス・ポート・ボリュームを1ファイルに書く）。ただし、今回の公式ページでは、次の点が確認できていません。

    • Windows コンテナの Compose ファイルの完成例（公式）公式未確認
    • Compose の volumes で、Windows のパス（c:\data）をどう書くか公式未確認
    • DB コンテナの公式の例（Lv1）公式未確認

    そのため、Windows 版では、完成した compose.yaml を載せていません。確認できた部分（Lv2〜Lv6 の docker run / docker network / docker volume）を、組み合わせて試してください。
