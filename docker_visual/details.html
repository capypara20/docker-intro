コンテナの基本

VM との違いと、Windows コンテナ・Linux コンテナの違い（分離モードの比較表つき）。

アプリ＋ 動くのに必要なファイル

軽くて速い。そのかわり「ホストのカーネルの種類」に縛られる。

  1. 土台はどちらも「ホストOS」。この上に、アプリを動かすための“箱”を作ります。
  2. VM：箱の中に「OSまるごと（自分専用のカーネル入り）」が入っています。そのぶん大きくて重い。
  3. コンテナ：OSは持たず、ホストOSのカーネルを共有します。中身はアプリと、動くのに必要なファイルだけ。
  4. だから軽くて速い。でも代わりに、ホストのカーネルの種類（Windows か Linux か）に縛られます。全体像のページ（Lv2）で、「カーネル」を分解して見られます。

  • Docker Docs「What is a container?」 … 複数のコンテナは同じカーネルを共有する

Windowsコンテナ と Linuxコンテナは、何が違う？

答えは「どのカーネルの上で動くか」です。

Windowsアプリ → Windowsコンテナ ／ Linuxアプリ → Linuxコンテナ。カーネルが違うものは混ぜられない。

  1. プロセス分離（従来のモード）：コンテナは、ホストとも他のコンテナとも同じカーネルを共有します。公式は「Linuxコンテナの動き方とほぼ同じ」と説明しています。
  2. Hyper-V分離：コンテナごとに最適化された軽量VMの中で動き、実質的に専用のカーネルを持ちます。ホストとバージョンが違っていても動かせます。
  3. Linuxコンテナは Linux のカーネルが必要です。Windows PC では、Microsoft製の Linux カーネルを持つ WSL 2 の上で動かします（Docker Desktop の場合）。公式に明記
  4. つまり、コンテナの種類はカーネルで決まります。Windowsアプリは Windowsコンテナ、Linuxアプリは Linuxコンテナ。公式の記述からの読み取り

ホストから見える？見える（Get-Process に出る）見えない（かわりに vmwp が見える）

Rozeさんの PC の実機確認（2026/10/5）
Windows 11 Home でも Windows コンテナが動き、既定の分離は hyperv、--isolation=process でも動いた。プロセス分離では ping がホストの Get-Process に見え、Hyper-V分離では見えなかった。これは上の公式の説明と一致しています。

イメージ

Rozeさんの Dockerfile からイメージができ、コンテナになるまでと、ビルドキャッシュの仕組み。

Dockerfile → イメージ → コンテナ（実例）

Rozeさんの docker/dockerimage ファイルを使っています。

Dockerfile（設計図）

FROM mcr.microsoft.com/windows/servercore:ltsc2025COPY hello.ps1 C:/app/CMD ["powershell", "-File", "C:/app/hello.ps1"]
コンテナ A書き込み層
コンテナ B書き込み層
🔒 イメージ（変更できない）
CMD 起動時に実行するコマンドの設定
COPY hello.ps1 が入った層読み取り専用
FROM 土台（servercore）の層読み取り専用
  1. まず Dockerfile（設計図）を書きます。これは Rozeさんの dockerimage ファイルの中身です。
  2. docker build：FROM の行で、土台になるイメージの層（レイヤー）が積まれます。
  3. COPY の行で、hello.ps1 が入った層がその上に積まれます。レイヤー ＝ ファイルの追加・削除・変更の差分です。
  4. CMD は「起動したら何を実行するか」の設定。これでイメージの完成です。完成したイメージはあとから変更できません（不変）。
  5. docker run：イメージには触らず、その上にコンテナ専用の「書き込み層」を1枚だけ乗せて起動します。
  6. 同じイメージから、コンテナをいくつでも起動できます。イメージは共有、書き込み層はコンテナごとに専用です。
  7. コンテナを消すと、消えるのは書き込み層だけ。イメージは無傷なので、すぐまた起動できます。
出典
  • Docker Docs「What is an image?」
  • Docker Docs「Understanding the image layers」 … 層の差分／不変／コンテナ専用の書き込み層／1つのイメージから複数のコンテナ

ビルドキャッシュ：1つ変えると、後ろは全部やり直し

FROM 土台のイメージ
RUN ツールをインストール
COPY アプリのコード ✎ ここを変更
RUN ビルド

↓ よく変わる命令ほど、下（後ろ）に書く

  1. 初回ビルド：Dockerfile の各命令が、それぞれ1つのレイヤーになります。
  2. 何も変えずに再ビルド：できあがったレイヤーをそのまま使い回すので、速く終わります。
  3. COPY の元ファイルを変更すると、そのレイヤーは作り直し。
    公式：「Whenever a layer changes, that layer will need to be re-built.」
  4. さらに、その後ろのレイヤーも全部やり直し。結果が同じでも再実行されます。
    公式：「Even if they wouldn't build anything differently, they still need to re-run.」
  5. ここから分かるコツ：よく変わる命令を後ろに書くと、やり直す範囲が小さくなります。仕組みからの読み取り（公式ページが直接そう勧めているわけではありません）
出典
  • Docker Docs「Docker build cache」 … 各命令 ＝ 1レイヤー／変更されたレイヤーと、その後ろのレイヤーは再実行
注意点
・「イメージを書き換える」ことはできません。変えたいときは、新しいイメージを作ります。
・docker image history で、各レイヤーのサイズと作成コマンドを確認できます（表示サイズは非圧縮）。

ネットワーク

ドライバーの種類（Linux と Windows）、名前での通信、ポート公開。

ドライバーの種類：Linux と Windows

▭ 箱の中の箱 ＝「〜の種類」

  1. ドライバーは、ネットワークの「種類（動き方）」を決める部品です。docker network create -d ドライバー名 で指定します。
  2. Linux 側：既定の bridge には2種類（デフォルト／ユーザー定義）があります。ほかに host・none・overlay・macvlan・ipvlan があります。
  3. Windows 側は名前が別です。既定は bridge ではなく nat。overlay は両方にあります。Linux の host / none を、そのまま当てはめないでください。

デフォルト bridge と ユーザー定義 bridge の動き

※ IPアドレスは説明用の例です。Linux 用 bridge の話です（Windows は、このページの「ドライバーの種類」と「ポート公開」を参照）。

デフォルト bridge
A172.17.0.2
b172.17.0.3
→ 172.17.0.3 → b ✕

✓ IPアドレスなら届く

✕ 名前（b）では届かない

ユーザー定義 bridge（my-net）
Amy-net
bmy-net
→ b
C未接続
Cmy-net
→ b ✕

✓ 名前（b）で届く ＝ 自動の名前解決

✕ つないでいない C からは届かない

✓ 動いたままでも参加できる

  1. --network を指定せずにコンテナ（A と b）を起動すると、自動でデフォルト bridge につながります。
  2. IPアドレスを指定すれば、A から b へ届きます。
  3. でも名前（b）では届きません。デフォルト bridge は名前を解決できず、必要なら旧式の --link が要ります。
  4. そこで docker network create my-net で自分用のネットワーク（ユーザー定義 bridge）を作り、A と b をつなぎます。
  5. ユーザー定義 bridge では名前でも通信できます。Docker 組み込みの DNS（127.0.0.11）が名前を解決します。
  6. さらに、つないだコンテナどうしだけが通信できる隔離も手に入ります。つないでいない C からは届きません。
  7. しかも実行中のコンテナでも、あとから接続・切断できます（docker network connect）。デフォルト bridge では、作り直しが必要です。
出典
  • Docker Docs「Bridge network driver」 … 名前解決／隔離／実行中の接続・切断の違い。デフォルト bridge は本番での利用が推奨されない
  • Docker Docs「Networking overview」 … 既定ネットワーク／ユーザー定義ネットワークの組み込みDNS（127.0.0.11）

ポート公開（-p）：外からコンテナへの入り口

外部ブラウザ・ほかのPC
Dockerホスト 8080 番
コンテナ80 番
外へ ← → 中へ ✕ → 中へ

✓ コンテナから外へ出る通信は、初期状態でできる

✕ 外からコンテナへは、そのままでは届かない

✓ -p 8080:80 ホストの 8080 番 → コンテナの 80 番へ転送

Windowsコンテナの既定ネットワークは bridge ではなく nat。ポート転送（マッピング）に対応しています。

  1. 登場するのは「外部」「Dockerホスト」「コンテナ」の3つ。コンテナはコンテナ内の 80 番ポートでアプリを待ち受けています。
  2. コンテナは初期状態でもネットワークが有効で、外へ出ていく通信はできます。
  3. でも外からコンテナの中へは入れません。ホストの外から届かせるには、入り口を開ける必要があります。
  4. --publish（-p）でポートを公開：ホストの 8080 番に来た通信を、コンテナの 80 番へ転送します。（8080:80 は書き方の一例）
  5. Windowsコンテナでは、既定のネットワークが nat です。ホストからコンテナへのポート転送（マッピング）に対応しています。
出典
  • Docker Docs「Networking overview」 … 外向きの接続／ホスト外からのアクセスには --publish（-p）
  • Microsoft Learn「Windows container network drivers」 … 既定は nat／ポート転送に対応

ボリューム

コンテナを消してもデータが残る流れと、bind mount との違い、置き場所の比較表。

ボリュームがあると、データが生き残る

イメージ（コンテナの元） 読み取り専用で変わらない。どのコンテナも、ここから作る ↓
コンテナ Aイメージから作成 ／ 書き込み層に保存 📄 data.txt ✕ 削除された（データも一緒に消えた）
コンテナ A′同じイメージから作成 ／ ボリュームに保存 ✕ 削除された
⇄
ボリューム myvol イメージにもコンテナにも属さない、別の置き場（実体は Dockerホスト上のディレクトリ） 📄 data.txt 不要なら docker volume prune
⇄
コンテナ B（新しい）同じイメージから作成 ／ 同じボリュームをマウント 📄 data.txt が読める
  1. コンテナはイメージから作られます。イメージは読み取り専用で変わりません。コンテナが書いたデータは、そのコンテナの書き込み層に入ります。
  2. コンテナを削除すると、書き込み層ごとデータも消えます。（イメージは無傷です）
  3. 対策：ボリュームを作ります（docker volume create）。イメージにもコンテナにも属さない、Docker が管理する別の保存場所です。
  4. 同じイメージから新しいコンテナを作り、ボリュームをマウントします。データは、ボリュームのほうに書かれます。
  5. コンテナを削除しても、ボリュームとデータは残ります。ボリュームはコンテナの寿命の外にあるからです。
  6. さらに新しいコンテナ B に同じボリュームをマウントすれば、データをそのまま引き継げます。複数のコンテナで共有することもできます。
  7. 注意：使われなくなったボリュームも自動では消えません。不要なら docker volume prune で整理します。
出典
  • Docker Docs「Volumes」 … 「Volumes are persistent data stores for containers, created and managed by Docker.」／コンテナを消しても残る／docker volume prune
  • Docker Docs「Storage」 … 「Data written to the container layer doesn't persist when the container is destroyed.」

ボリューム と bind mount（どちらも「外に置く」方法）

bind mount

ホストのフォルダ例：C:\work\data（自分で場所を決める）
⇅ そのまま共有
コンテナの中マウント先のパス
  • ホストのフォルダ構造・OS に依存する
  • ホストからも、コンテナ内と同じファイルを触れる

ボリューム

Docker が管理する領域場所は Docker にお任せ
⇅ マウント
コンテナの中マウント先のパス
  • Docker が完全に管理（ホストの中核機能から分離）
  • バックアップ・移行がしやすい
  • Docker のコマンド・APIで管理できる
  • 複数のコンテナで比較的安全に共有できる

ホストからも編集したい → bind mount ／ コンテナのデータを安全に残したい → ボリューム

  1. どちらも「データをコンテナの外に置いて、コンテナの中に見せる」方法です。何が違うのでしょう。
  2. bind mount：ホストの好きなフォルダを、そのままコンテナに見せます。ホストのフォルダ構造や OS に依存します。
  3. ボリューム：置き場所の管理を Docker に任せます。バックアップや移行がしやすく、Docker のコマンドで管理できます。
  4. 使い分け：ホストからも同じファイルを触りたいなら bind mount、コンテナのデータを安全に残したいならボリューム。公式の説明からの読み取り
出典
  • Docker Docs「Volumes」 … bind mount との違い／ボリュームの利点
  • Docker Docs「Storage」 … 保存先の違い（ボリューム：デーモンが管理／bind mount：ホスト上の任意の場所）

データの置き場所の比較

置き場所ホスト上の保存先コンテナを消すと向いている用途
書き込み層コンテナ専用の層消える一時的な変更
ボリュームDocker が管理する領域残る長期保存・性能が必要な処理
bind mountホスト上の任意の場所残る（ホスト側にあるため）ホストとコンテナの両方からファイルを扱う
tmpfs mountホストのメモリ上（ディスクに書かない）残らない（停止・再起動で消える）一時的なキャッシュ・機密情報
注意点
・ボリュームは Linux コンテナと Windows コンテナの両方で使えると公式に書かれています。
・公式は「ボリュームのデータに、ホストから直接触れるのは非対応」としています。ホストから触りたいときは bind mount を使います。
・Windows コンテナでの bind mount・ボリュームの書き方は、Microsoft Learn「Persistent storage in containers」に例があります（実例ページの Lv6 を参照）。一方、tmpfs が Windows コンテナで使えるかは、公式ページで確認できていません。tmpfs は公式未確認
・Windows のコンテナ側の公式ページでも、ホストのファイルやボリュームをコンテナに見せることは「隔離の境界を破る操作」と説明されています。意図して使う操作です。
