  1. ① VM：VM は「自分のカーネルを含む完全な OS」を動かします。その中に Linux を入れ、Docker Engine で Linux コンテナを動かす方法です。（VM ソフトの具体名は、一般的な話です）
  2. ② Docker Desktop：既定のバックエンドは WSL 2。コンテナは、WSL 2 の中の専用ディストリビューション（docker-desktop）で動きます。大きな組織では有償です。
  3. ③ WSL 2 ＋ Engine：Ubuntu などの WSL 2 ディストリビューションに、Docker Engine を直接入れます。Docker Desktop は不要。Docker Engine 自体のライセンスは変わっていません。
  4. ④ Windows 上の Engine：Windows コンテナを動かす方法。Windows Server では Moby・Mirantis・containerd。Windows 10/11 は、公式には「Pro / Enterprise ＋ Hyper-V」。Rozeさんの PC（Home）では動きましたが、公式の要件の外の可能性があります。

② コンテナ技術の全体地図

OCI・runc・containerd・Docker Engine・Podman・Kubernetes は、どういう関係？ 下の「規格」から、上の「クラスタ管理」へ積み上げます。

コンテナ技術の全体地図（下から積み上げる）

上ほど「利用者に近い」並びです。層の分け方は筆者の整理（公式の分類ではありません）。箱をクリックすると、公式の説明と出典が出ます。

  1. 規格（OCI）：コンテナの形式とランタイムの業界標準。3つの仕様（Image / Runtime / Distribution）があります。2015年6月に Docker、CoreOS などが発足させました。
  2. 低レベルランタイム：コンテナのプロセスを実際に作る部分。runc は、Docker が OCI に寄贈したものです。Podman のページには、runc と並んで crun が挙がっています。
  3. コンテナランタイム：containerd は、コンテナのライフサイクル全体（イメージの転送と保存、コンテナの実行と監視など）を管理します。Linux と Windows の両方にあります。CRI-O も、Kubernetes のランタイムの例です。
  4. エンジン・ツール：Docker Engine、デーモンを持たない Podman、containerd 用の Docker 互換 CLI nerdctl。Podman は、OCI 準拠のランタイム（runc、crun など）に頼ってコンテナを作ります。
  5. Kubernetes：各ノードに、CRI に準拠したコンテナランタイムを入れて使います。例は containerd・CRI-O・Docker Engine・Mirantis Container Runtime。Docker Engine との直接統合（dockershim）は 1.24 で削除されました。
名前何をするもの（公式の説明）ひとこと
OCIコンテナの形式とランタイムの業界標準を作るプロジェクト。Runtime / Image / Distribution の3仕様みんなが守る「決まりごと」
runcDocker が OCI に寄贈した、コンテナの形式とランタイム（「cornerstone」）コンテナを実際に起動する部品
containerdホスト上のコンテナのライフサイクル全体を管理する、業界標準のコンテナランタイム。CNCF の卒業プロジェクトKubernetes でも、Windows Server でも使える
Docker Engineサーバー（dockerd）・API・CLI（docker）の3つでできた、クライアント・サーバー型のアプリいつもの docker コマンド
Podmanコンテナやイメージを扱うツール。デーモンを持たず、Docker に似た CLI を持つ。root でも一般ユーザーでも実行できるdocker の代わりに使える
Kubernetes各ノードに CRI 準拠のコンテナランタイムを入れて、Pod を動かす大規模に管理する仕組み
注意点
・「dockerd が containerd を呼び、containerd が runc を呼ぶ」という呼び出しの順は、今回取得した公式ページには明記がありませんでした（containerd のページに、採用事例として Docker が挙がっているだけです）。図では、この呼び出しの順を描いていません。公式未確認

③ アプリ別：どれを使う？

決め手は「そのアプリは、Linux でも動くか」。コンテナはホストのカーネルを借りて動くので、ここが最初の分かれ目です。

アプリ別の選び方（判断の流れ）

判断の流れは筆者の整理です。各アプリの対応 OS は、Microsoft の公式ページで確認した範囲を示します。

開発：WSL 2 ＋ Docker Engine（または Docker Desktop）
本番：Linux サーバー・クラウド
開発：Windows 11 Pro / Enterprise ＋ Docker Desktop（Windows コンテナ）
本番：Windows Server ＋ Docker Engine。イメージの版（ltsc2022 など）を本番に合わせる
  1. 最初の問いは、「そのアプリは Linux でも動くか」。コンテナはホストのカーネルを借りるので、Windows 用のアプリは Windows コンテナ、Linux 用のアプリは Linux コンテナになります。
  2. Linux でも動く例：PowerShell 7（Windows・macOS・Linux で動く）、.NET（クロスプラットフォーム）、PostgreSQL などの DB（公式イメージは Linux 向け）。
  3. これらはパターン B（Linux コンテナ）。開発は WSL 2 ＋ Docker Engine（または Docker Desktop）、本番は Linux サーバーやクラウドです。読み取り
  4. Windows 専用の例：.NET Framework（Windows アプリと Web サービス向け。IIS が、そのランタイムをホストできる）、Windows PowerShell 5.1（.NET Framework 上に作られている）。
  5. これらはパターン A（Windows コンテナ）。開発は Windows 11 Pro / Enterprise ＋ Docker Desktop、本番は Windows Server ＋ Docker Engine。イメージの Windows の版を、本番に合わせます。
  6. GUI を操作するアプリや Excel の操作は、コンテナには向かないと、筆者は整理しています。そのままの PC か VM で動かす想定です。公式未確認
